# 闭环UI优化与运行数据/案例库增强

关联分支：`20260708094040-13-闭环UI优化与运行数据案例库增强`
参考实现：`references/agent-frontend`（仅借鉴前端结构与列表/卡片/检索交互，禁止 import/提交其代码）
行业案例数据源：`data/expert_knowledge.md`（19 场景 / 1314 案例）

## 背景

当前前端「排队溢出九幕演示」已跑通端到端（`frontend/`，分支 main，`localhost:5173`）。产品评审后提出四类 UI 优化，目标是把「NLU 理解、运行数据、案例库、问题验证 + 治理策略」做得更像截图中的目标形态，提升可读性与可信度。

现状与目标截图的关键差异：
- 截图中的 tab（理解过程 / 行业案例 / 路口案例）与逐进口/逐转向运行指标、独立「问题验证」卡，均为**目标设计**，当前 `frontend/src` 尚未实现（只在 `docs/design/*`、`modules/run_1.py` 出现过这些文案）。
- 逐进口/逐转向饱和度、方向失衡、服务水平等富数据**已在 PG 装载层算出**（`app/data/load_intersection_from_pg.py::_aggregate_metrics` 的 `movement_saturation`、`raw.turn_saturation/green_utilization/evaluation`、`metrics.imbalance_index`、`los`），但被 `app/data/pg_adapters.py::metrics_for_diagnosis` 收敛为**单一目标转向**，未透传到公开的 `diagnosis.metrics`。因此运行数据面板属于**透传/序列化增强**，而非新增计算。

## 布局决策（已与产品确认：保持两栏不交换）

沿用现有两栏布局，不做整体交换：
- **左栏**：`UnderstandingPanel`（理解面板）——承载 NLU 理解 + 经验库 + **案例库重构**（行业案例 / 路口案例）。
- **右栏**：`ProcessPanel`（处置闭环时间线）——承载 NLU 诊断工单卡、**详细运行数据卡**、**新增问题验证卡**、**新增治理策略卡**、方案等证据卡。

> 说明：R3 文案「呈现在左侧运行卡片」在「不交换两栏」的约束下，落位为**处置闭环流中的详细运行数据卡**（诊断阶段揭示），做数据详细化；如后续确需将其物理移至最左独立栏，另立需求。

## 需求项

### R1 · NLU 诊断对象识别卡改为无序列表并补齐字段
文件：`frontend/src/cards/DiagnosisTicketCard.vue`
- 由当前 2 列 `<dl>` 网格改为**紧凑无序列表**（`<ul>`，label + value 单行、行距更小）。
- 全中文标签（沿用 `labels/enums.ts` 的 `t()`）。
- 补齐更多 NLU 理解字段，至少包含：
  - **原始问题**：来自前端 `store.userInput`（用户输入原文），置于列表首行。
  - 对象、路口（含 `inter_id`）、时间（含 period）、方向转向、问题、**诊断范围**（`diagnosis_scope`）、治理目标、约束、解析置信度 + 匹配方式。
  - 若存在 `intersection_name_candidates` / `match_candidates`，以次要行或提示形式展示（择一，YAGNI）。
- 减小整卡内边距与项间距，保证信息密度接近截图。

### R2 · 案例库重构为「行业案例 / 路口案例」结构化全量展示
文件：`frontend/src/panels/UnderstandingPanel.vue`（案例库 tab）+ 新增数据/解析
- 案例库子 tab 改为 **行业案例** / **路口案例**：
  - **行业案例**：数据来自 `data/expert_knowledge.md`，**构建期解析为精简 JSON 打包进前端**（离线可用，无需后端接口）。展示**全部 19 个场景**，结构化层级对齐截图 2：
    - 场景（如「主干道干线绿波协调 189 例」）→ 场景描述 → `典型问题·XX（NN 次）`（典型表现）→ `治理方案·YY（NN）`（关键措施 / 适用条件 / 注意事项）→ 代表案例（`[#id] 标题：摘要…`，可展开/收起）。
    - 顶部提供**搜索框**「搜索场景 / 典型问题」，支持按场景名、典型问题、关键措施过滤。
    - 长列表默认折叠，点击展开（参考 `references/agent-frontend` 的 `<details>`/collapsible 与 `.scenario-category-list`、`issue-card` 列表样式）。
  - **路口案例**：来自「用户确认后下发沉淀的案例」+ 当前 `cause.case_cards`/`similar_cases`（`store.existingCases`）。展示历史诊断/治理方案条目（标题、相似度、措施、结果、经验、`case_id`）。
- 每条案例可被右栏「治理策略卡」的参考依据点击定位（见 R4）。

### R3 · 详细运行数据面板（逐进口 / 逐转向 / 失衡 / 服务水平）
前端：`frontend/src/cards/DataMetricsCard.vue`；后端：透传富指标
- 面板信息对齐截图 4：
  - 头部：路口名 + `inter_id`、进口车道概况（`N 进口 · M 车道`）、关注/保护方向标签（若可得）。
  - 运行数据列表：**逐进口饱和度**（东/西/北…）、**延误指数**、**服务水平**（LOS，F 标「阻塞」）、**逐转向饱和度**（东左转/西左转/北直行/东直行…，超阈值标「过饱和 / 偏高」）、**逐转向绿灯利用率**、**方向失衡**（imbalance_index，标「各进口差异大」）。
  - 每项带阈值着色（过饱和/偏高/正常），沿用 `utils/format.ts` 色调逻辑。
- **后端透传**（fullstack）：在 `skills/data-analysis-diagnosis/scripts/analyze_overflow.py` 的返回中新增结构化块（如 `metrics.by_approach`、`metrics.by_movement`、`metrics.imbalance_index`、`metrics.los`、进口/车道计数），数据源为 `context.task["metrics"]` 与 `pg_raw`（`turn_saturation`/`green_utilization`/`evaluation`），不新增计算、不编造；缺失时字段留空并优雅降级。前端 `frontend/src/api/types.ts` 同步类型。

### R4 · 新增「问题验证卡」+「治理策略卡」（含可点击参考依据）
前端：新增 `frontend/src/cards/ProblemVerificationCard.vue`、`frontend/src/cards/GovernanceStrategyCard.vue`；接入 `ProcessPanel`
- **问题验证卡**（紧挨处置闭环，对齐截图 5 上半）：
  - 常发性、周期性、运行状态（饱和度 + 服务水平）、配时画像（周期约 X s、日计划时段 N 个）。
  - 数据源：运行状态/配时画像来自 `diagnosis.metrics`/PG `signal`（`current_cycle_s`、`time_plan_count`）；**常发性/周期性后端当前无专用指标**，本需求新增**轻量派生判定**（基于同时段规律的启发式，明确标注为「派生」，不编造精确数值）。
- **治理策略卡**（对齐截图 5 下半「治理建议 + 参考依据」）：
  - 治理建议要点（箭头列表，来自 `strategy`/`plan` 推荐理由与执行策略）。
  - 底部「参考依据」为**可点击 chips**：如「一般路口优化」（行业场景）、`011wwe28ctu00001`（路口案例）。点击后：
    - 打开左栏案例库并切到对应子 tab（行业案例 / 路口案例），滚动定位到对应条目并高亮（参考 `references/agent-frontend` 的选中态 `.result-item.active` + `scrollIntoView`；复用现有 `window` 事件 `open-case-library` 机制扩展参数）。
    - 点击后的高亮/展开样式对齐截图（选中项描边高亮 + 展开详情）。
  - 参考依据来源：`strategy.case_references` / `cause.case_cards`（路口案例 `case_id`）+ 场景匹配（行业案例场景名）。后端如缺字段则透传已有的 case_id / 场景标签。

## 后端需补齐（fullstack）

1. **富指标透传**：`analyze_overflow` 输出补充 `by_approach`（逐进口饱和度/延误/LOS）、`by_movement`（逐转向饱和度/绿灯利用率）、`imbalance_index`、`los`、进口与车道计数；源自 `task.metrics` 与 `pg_raw`，禁止占位/编造，缺失显式为空。
2. **配时画像透传**：把 PG `signal.current_cycle_s`、`time_plan_count`（及必要的 plan_name）透出到诊断响应，供问题验证卡使用。
3. **常发性/周期性派生**：新增轻量启发式（可基于 `raw.flow_correlate` 同 `day_of_week`/period 规律或同时段压力），产出结构化 `{recurring: bool/label, periodic: label, basis}`，明确「派生」来源；无依据时降级为「数据不足」。
4. **参考依据字段**：确保治理策略可取到 `case_id`（路口案例）与场景标签（行业案例），必要时在 strategy/response 层补齐透传。
5. `frontend/src/api/types.ts` 与 `frontend/src/mock/run_1_fixture.json` 同步新增字段（重采或手工补齐 mock，保证前端离线开发与测试）。

## 验收标准

1. **R1**：诊断工单卡为无序列表、行距更紧凑、全中文，首行展示用户原始问题，字段含诊断范围等新增项；`npm run build` 与单测通过。
2. **R2**：案例库「行业案例」展示全部 19 场景的结构化层级（场景→典型问题→治理方案→代表案例），搜索可用、可展开收起；数据来自 `expert_knowledge.md` 构建期 JSON；「路口案例」展示沉淀/相似案例。
3. **R3**：运行数据面板呈现逐进口/逐转向饱和度、绿灯利用率、延误指数、服务水平、方向失衡，阈值着色正确；后端对 `011wwe28ctu00001`（或现有 mock 路口）透出对应富指标，缺失优雅降级。
4. **R4**：问题验证卡与治理策略卡显示在右栏处置闭环流中；治理策略「参考依据」chips 可点击，点击后左栏案例库切换子 tab 并定位高亮到对应行业/路口案例。
5. **回归**：`.venv` pytest 全绿（含新增后端透传/派生单测）；前端 `npm test` + `build` 通过；`references/agent-frontend` 代码未被 import。

## 非目标（本次不做）

- 不做两栏物理交换、不新增第三独立栏。
- 不接入真实历史「常发性/周期性」大数据统计（仅轻量派生 + 明确标注）。
- 不改动地图图层、方案生成配时链路（需求 12 已覆盖）。
