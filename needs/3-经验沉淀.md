# 需求 3：经验沉淀

## 需求概述

在需求 2（生产化优化）第九幕简化版（`POST /api/v1/agent/plan/decision` → `plan_feedback.jsonl`）基础上，完善**用户经验输入拆分**与**方案反馈闭环**，形成可检索、可溯源、可复用的经验体系。`knowledge_qa.jsonl` 为外部教科书案例库，**只读检索，禁止写入**。

## 与需求 2 的边界

| 需求 2（已完成/进行中） | 需求 3（本需求） |
|------------------------|-----------------|
| 第九幕简化版：accept/reject 写入 `plan_feedback.jsonl` | 方案反馈完整沉淀 + 后续检索引用 |
| 意图理解输出 `diagnosis_ticket` 单一体 | NLU 拆分认知/诊断/方案三类用户经验 |
| 案例检索仅 `knowledge_qa.jsonl` | 叠加用户经验库 + 已接受方案库检索 |
| 计划写入 `knowledge_qa.jsonl`（已取消） | 明确禁止；反馈只写独立 jsonl |

---

## 需求条目

### 1. 用户经验三类拆分（NLU 阶段）

用户在自然语言中可能同时携带三类经验，**不一定全部出现**；`intent_understanding` Skill 须在 NLU 阶段识别并结构化输出：

| 类型 | 含义 | 示例（同一句输入中的片段） |
|------|------|---------------------------|
| **认知经验** | 路口画像 / 问题现象 | 「xx 路口下午 3 点经常拥堵」 |
| **诊断经验** | 用户对成因的主观判断 | 「这附近有一个小学那时候放学家长接送孩子导致的」 |
| **方案经验** | 用户提出的处置建议 | 「应该增加一点绿灯时间」 |

**要求：**

- 扩展 `intent_understanding` 的 LLM prompt 与输出 schema，新增 `user_experiences` 字段（数组，元素含 `experience_type`、`content`、`source_span`）
- 每条经验附带完整标签体系（见下节），并写入 `data/user_experience.jsonl`
- 诊断工单 `diagnosis_ticket` 仍保持剧本第一幕字段，与经验拆分并存，不得互相替代

### 2. 经验标签体系

三类经验各自有完整标签，供后续检索与引用：

| 经验类型 | 必填标签 | 可选标签 |
|----------|----------|----------|
| 认知经验 | `inter_id`/`intersection_name`、`problem_type`、`time_period` | `direction`、`movement`、`spatial_structure`、`severity` |
| 诊断经验 | `cause_dimension`（对齐六维）、`cause_keywords` | `related_poi`（学校/医院等）、`time_period`、`confidence` |
| 方案经验 | `strategy_action`（如加绿/控流/协调） | `target_phase`、`adjustment_direction`、`constraints` |

标签定义文件：`app/data/intersection_config/experience_tag_schema.yaml`（新建）。

### 3. 经验检索与下游引用

在成因分析、策略生成、方案生成阶段，除检索 `knowledge_qa.jsonl` 外，须叠加检索：

- `data/user_experience.jsonl`（用户输入沉淀）
- `data/plan_feedback.jsonl` 中 `decision=accept` 的记录（可接受方案）

**引用逻辑示例：**

- 成因分析：若用户曾输入「附近有学校、下午接送导致拥堵」类诊断经验，且路口/时段匹配，纳入 `cause_ranking` 佐证
- 方案生成：若用户曾建议「加绿灯时间」，在候选方案说明中标注用户方案经验；若存在相似路口已接受方案，可溯源引用 `trace_id` + `plan_id`

### 4. 方案接受/否决沉淀（第九幕完整版）

用户对方案点击**接受**或**否决**：

- **只追加写入 jsonl**，不修改 `knowledge_qa.jsonl`
- 写入路径：沿用 `data/plan_feedback.jsonl`（扩展 schema）
- 接受方案须包含：方案快照、诊断上下文、路口拓扑指纹、关键指标摘要、标签，支持后续相似场景检索与溯源
- 否决方案须包含：否决理由、被否决方案特征摘要，供方案生成阶段降权或规避同类策略

**非目标（本期不做）：**

- KPI 执行效果对比、`evaluation-feedback` Skill 全量接入
- 「修改后再生成」交互（可留 API 扩展位）
- 向 `knowledge_qa.jsonl` 追加任何记录

### 5. 配置与约束

- 遵循 `docs/rule.md`：经验与反馈数据真源为 jsonl + `task` 注入；禁止 demo 静默 fallback
- 剧本第九幕验收标准以 `docs/剧本.md` 为准；本需求补齐「经验闭环」数据面，UI 仍不在本期范围
- 开发前阅读 `bugs/`；详细计划见 `plans/3-经验沉淀.md`

## 反思：与 `docs/剧本.md` 第九幕的差异

| 剧本要求 | 需求 2 现状 | 需求 3 目标 |
|----------|------------|------------|
| 接受/拒绝/沉淀案例 | 简化版 accept/reject | 完整标签 + 可检索沉淀 |
| 关联路口/时段/成因/策略 | 仅 `diagnosis_ticket` 快照 | 拓扑指纹 + 指标摘要 + 标签 |
| 推荐案例 / 风险案例 | 仅 `knowledge_qa` 只读 | 叠加用户接受方案 + 否决规避 |
| 专家口播中的经验引用 | 无用户经验通道 | NLU 拆分 + 全链路检索 |
| 一次处置变可复用案例 | 写日志无检索 | 接受方案可溯源引用 |

## 验收标准

- [x] `intent_understanding` 输出含 `user_experiences[]`，三类经验可空、可部分、可全部
- [x] 用户经验写入 `data/user_experience.jsonl`，每条含 `experience_type` 与完整标签
- [x] `knowledge_qa.jsonl` 在生产路径上无任何写入操作（只读）
- [x] `POST /api/v1/agent/plan/decision` 接受/否决记录含扩展字段（拓扑指纹、指标摘要、标签）
- [x] 成因分析检索结果含 `user_experience_refs`（用户诊断经验命中）
- [x] 方案生成检索结果含 `accepted_plan_refs`（相似已接受方案）与 `rejected_plan_avoidance`（否决规避提示）
- [x] 全量 `pytest` 通过；新增用例覆盖 NLU 拆分、经验写入、反馈检索
