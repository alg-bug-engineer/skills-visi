## 一、需求定位

本次优化只面向“路口进口道排队溢出”问题，目标不是建设覆盖所有交通问题的通用智能体，而是基于当前有限但真实可用的数据、流量溯源结果、相邻路口状态和现状信号方案，形成一条逻辑自洽、结论可信、方案可验证的溢出治理闭环：

> 识别溢出对象
> → 确认溢出状态
> → 判断队列为什么无法消散
> → 确认车辆是否可以继续向下游释放
> → 选择唯一适用的治理路径
> → 生成与治理策略一致的方案
> → 校验、试运行、监测和回滚。

当前系统已经形成“意图理解—数据诊断—成因分析—策略生成—方案生成”五阶段 Skill 流水线。

但目前各 Skill 主要通过自由结构的 `artifacts` 传递结果，运行时重点检查阶段是否成功和是否存在全部 artifact，并未系统校验前后阶段的交通语义是否一致。

因此，本次优化的核心不是增加更多分析步骤，而是建立：

> **统一事实状态、溢出机制判别、策略决策契约、方案语义校验和试运行反馈闭环。**

# 二、总体优化目标

## 2.1 总体目标

基于当前 Case A 的真实数据和 fixture 数据，形成一个能够完成以下任务的排队溢出闭环智能体：

1. 准确锁定用户所说的目标路口、进口方向和转向；
2. 区分“已经发生溢出”“接近溢出”“排队较长但尚有空间”和“数据不足”；
3. 识别排队无法消散的主要机制，而不是简单把所有高排队归因于信号控制不当；
4. 判断直接下游是否具备真实承接空间；
5. 根据溢出机制选择唯一适用的治理方向；
6. 将治理策略转换为明确、可校验的信号调整要求；
7. 确保最终配时结果没有偏离前面的治理逻辑；
8. 对证据不足的场景允许输出“先核验、暂不调整”；
9. 对可试验场景输出小步、可回滚、可观测的条件性方案；
10. 通过实施前核验、实施中监测和实施后评估形成闭环。

## 2.2 可信目标

系统输出的每个关键结论都必须回答三个问题：

* 结论依据是什么；
* 结论置信度有多高；
* 还缺什么证据。

禁止仅因为流程需要继续，而强制生成：

* 唯一主因；
* 可执行配时；
* 下游承接不足；
* 信号控制不当；
* 干线协调方案。

## 2.3 可行目标

最终方案必须满足：

* 能对应到具体目标转向；
* 能对应到具体相位或阶段；
* 能计算目标有效绿的实际变化；
* 能解释时间从哪个阶段转移而来；
* 能验证周期、最小绿、最大绿、行人清空等约束；
* 能设置实施前提、监测指标和回滚条件；
* 在当前数据条件不足时，不伪装为可直接执行方案。

# 三、需求边界

## 3.1 本次纳入范围

本需求只处理单个目标进口或目标转向的排队溢出问题，覆盖：

* 目标路口和目标转向识别；
* 进口道排队空间风险判断；
* 直接下游流向溯源；
* 下游承接能力判断；
* 上游来车压力判断；
* 目标方向放行状态分析；
* 溢出机制分类；
* 单点小步配时；
* 下游保护；
* 简单上下游联控建议；
* 实施前核验；
* 条件性执行；
* 监测和回滚；
* 专家经验辅助。

## 3.2 暂不纳入范围

本需求不负责解决：

* 空放、失衡、一般拥堵、行人冲突等其他问题类型；
* 当前临时统计口径的全面重构；
* 全路网动态优化；
* 自适应信号控制系统；
* 多路口统一周期和绿波方案的完整求解；
* 现场设备控制指令直接下发；
* 实时视频识别算法建设；
* 交通仿真平台建设；
* 全量行业案例知识库升级；
* 对所有城市、所有路口的生产泛化。

## 3.3 当前指标的使用边界

当前排队比、饱和度、绿灯利用率等指标可以继续用于：

* 筛选典型路口；
* 描述风险；
* 构造 Case；
* 支撑演示闭环；
* 触发进一步核验。

但应明确区分两种用途：

```text
展示和筛查级指标：
可以用于发现问题和描述异常。

决策级指标：
可以直接决定治理分支或配时动作。
```

当前临时构造或统计口径未完全统一的指标，应标记为：

```json
{
  "quality_level": "demo_proxy",
  "decision_eligible": false
}
```

它可以参与风险说明，但不能单独证明“信号控制不当”或直接驱动大幅配时调整。

# 四、当前 Case A 基础事实

目标问题：

> 解放东路与齐川路路口，北向南直行，晚高峰排队外溢。

当前关键指标：

* 排队比约 0.97；
* 排队长度约 107.8 米；
* 进口道蓄车长度约 110.78 米；
* 剩余空间约 2.98 米；
* 饱和度约 0.55；
* 绿灯利用率约 0.27；
* 方向失衡约 0.15。

现有数据能够支持：

> 目标进口排队已经非常接近进口道空间边界，存在明显溢出预警。

系统现有风险规则本身也将排队比 0.8—1.0 定义为溢出预警，超过 1.0 才定义为突破空间边界。

直接下游为：

> 永绥路与齐音路路口。

现有数据表现为：

* 下游排队约 1 米；
* 排队比约 0.01；
* 剩余蓄车空间约 115 米；
* 暂未发现明显下游排队阻塞。

因此，基于当前 Case 数据，可以得到三个相对可信的事实：

1. 目标进口存在高等级溢出风险；
2. 直接下游暂未表现出明显承接不足；
3. 目标进口“高排队、低绿灯利用率”并存，形成机制尚未确认。

不能直接得出：

* 下游接不住；
* 绿灯给了也用不上已经被证实；
* 信号控制不当是唯一主因；
* 只要增加绿灯就一定有效。

# 五、整改后的 Case A 目标结论

Case A 应当收敛为下面这条主逻辑。

## 5.1 溢出状态

结论：

> 北向南直行排队已接近进口道蓄车空间边界，处于溢出预警状态。

可信等级：

> 高。

依据：

* 排队比约 0.97；
* 剩余蓄车空间约 3 米。

需要保留的表述：

> 用户反映存在实际外溢；当前指标确认高等级外溢风险。是否已经跨越进口道边界，可由视频或连续轨迹进一步确认。

## 5.2 下游状态

结论：

> 直接下游初步具备承接余量，暂不支持“下游整体接不住”。

可信等级：

> 中等。

依据：

* 直接下游排队较短；
* 排队比低；
* 剩余蓄车空间较大。

保留条件：

> 下游饱和度、绿灯利用率等关键指标部分缺失，因此不能把“有承接余量”表达成绝对结论。

## 5.3 成因状态

结论：

> 当前确认了高排队与低绿灯利用并存，但尚不能唯一归因。

优先核验方向：

1. 目标进口放行效率、渠化或车道利用异常；
2. 检测或统计口径异常；
3. 上游车团到达与目标相位时序不匹配；
4. 有效绿分配不足；
5. 下游局部出口阻塞，当前证据较弱。

## 5.4 治理决策

主策略：

> **先验后调。**

完整表述：

> 先核验目标队列在绿灯期间的实际消散情况、出口通行条件和检测有效性；确认直接下游畅通且绿灯结束时目标队列仍无法消散后，再实施目标方向小步增绿试验。

## 5.5 方案状态

当前 Case 在没有补充核验结果时，最终状态应为：

```json
{
  "plan_status": "conditional",
  "executable": false,
  "decision": "verify_then_adjust",
  "reason": "目标进口高排队低利用的形成机制尚未完成核验"
}
```

为了演示完整配时闭环，可在 fixture 中显式加入核验结果：

```json
{
  "verification": {
    "source_type": "fixture_assumption",
    "downstream_path_clear": true,
    "detector_valid": true,
    "queue_remains_at_green_end": true,
    "channelization_blocked": false,
    "passed": true
  }
}
```

前端必须明确显示：

> 典型案例核验前提。

不能把该结果表达成来自实时数据库的已确认事实。

# 六、溢出专用机制模型

系统不再使用开放式通用成因分析，而应固定为五类溢出机制。

## 6.1 下游回堵型

代码：

```text
downstream_blocked
```

判定特征：

* 目标进口排队高；
* 直接下游排队比高、剩余空间不足或明确 blocked；
* 继续增加目标放行可能导致下游溢出。

治理方向：

* 先保护下游；
* 抑制继续向下游送车；
* 必要时上游控流；
* 禁止单点增绿。

## 6.2 本路口放行不足型

代码：

```text
local_release_insufficient
```

判定特征：

* 目标进口排队高；
* 下游有承接余量；
* 目标方向需求和绿灯利用率较高；
* 绿灯结束时队列仍明显未消散。

治理方向：

* 小步增加目标有效绿；
* 周期原则上保持不变；
* 从低压力阶段借时；
* 短周期试验并监测。

## 6.3 放行效率异常型

代码：

```text
discharge_anomaly
```

判定特征：

* 排队高；
* 绿灯利用率低；
* 下游无明显阻塞；
* 单纯增加绿灯是否有效无法确认。

可能原因：

* 出口受阻；
* 车道利用不均；
* 渠化不匹配；
* 违停或公交停靠；
* 机非干扰；
* 检测器异常；
* 排队与绿灯利用率时间口径错位。

治理方向：

* 先核验；
* 暂不直接生成可执行配时；
* 核验通过后转入小步释放。

Case A 当前应优先落在这一分支。

## 6.4 上游冲击型

代码：

```text
upstream_arrival_shock
```

判定特征：

* 上游到达强度高；
* 来车呈短时集中；
* 目标进口蓄车空间不足；
* 单点增绿无法稳定吸收来车。

治理方向：

* 上游削峰；
* 调整放行节奏；
* 必要时协调相位差；
* 同时小步释放目标方向。

## 6.5 证据不足型

代码：

```text
evidence_insufficient
```

判定特征：

* 溢出风险可能存在；
* 但下游、目标放行状态或现状配时数据不足；
* 无法区分上述机制。

治理方向：

* 输出补证任务；
* 仅生成核验方案；
* 不生成可直接执行配时。

建议在现有 `SkillContext` 中增加溢出专用状态对象。

当前 `SkillContext` 主要包含自由结构的 `task` 和 `artifacts`。

建议新增：

```python
@dataclass
class OverflowCaseState:
    identity: OverflowIdentity
```

# 八、五阶段详细需求

## 8.1 第一阶段：溢出对象识别

### 目标

从用户自然语言中识别唯一治理对象。

### 输入

* 用户描述；
* 路口名称；
* 时间范围；
* 方向；
* 转向；
* 问题类型；
* 用户约束。

### 输出

```json
{
  "problem_type": "spillback",
  "inter_id": "...",
  "direction": "北向南",
  "movement": "直行",
  "movement_key": "d0_t2",
  "time_window": "17:00-19:00",
  "constraints": [
    "避免加重下游拥堵"
  ]
}
```

### 规则

* 当前系统只接受 `spillback`；
* 方向或转向不明确时，不得静默默认；
* 识别完成后生成不可变 `OverflowIdentity`；
* 后续阶段引用其他方向或其他下游时，触发对象一致性错误。

---

## 8.2 第二阶段：溢出状态确认

### 目标

回答：

> 目标进口目前处于什么空间风险状态？

### 输出状态

```text
normal
queue_high
spillback_warning
spillback_confirmed
unknown
```

### Case A 目标输出

```json
{
  "status": "spillback_warning",
  "confidence": 0.9,
  "queue_ratio": 0.9731,
  "remaining_storage_m": 2.98,
  "message": "目标进口排队接近进口道空间边界"
}
```

### 必须输出

* 排队长度；
* 库容长度；
* 排队比；
* 剩余空间；
* 指标来源；
* 指标质量；
* 是否为实际溢出证据；
* 是否需要视频或轨迹确认。

### 禁止输出

* 信号控制不当；
* 下游接不住；
* 应当增加绿灯；
* 应当上游控流。

这些不属于状态确认阶段。

---

## 8.3 第三阶段：溢出机制判别

### 目标

回答：

> 队列为什么无法在目标路口正常消散？

### 判别顺序

第一步：判断直接下游状态。

```text
blocked → 下游回堵型
slack → 继续判断目标放行状态
unknown → 证据不足型
```

第二步：判断目标方向放行状态。

```text
高需求 + 高绿灯利用率 + 下游有余量
→ 本路口放行不足型

高排队 + 低绿灯利用率 + 下游有余量
→ 放行效率异常型
```

第三步：判断上游冲击。

```text
上游集中到达显著
→ 可作为主机制或次要因素
```

### 输出

只输出一个主机制。

允许附带一个次要因素，但不能生成多个互相平行的“主因”。

### 大模型职责

大模型只负责：

* 解释结构化机制判断；
* 组织专家语言；
* 说明缺失证据；
* 生成核验任务。

大模型不得：

* 修改机制编码；
* 修改下游状态；
* 改写目标对象；
* 将 hypothesis 自行提升为 confirmed。

当前成因 Skill 的提示词要求模型直接“判断主因”，这是需要调整的部分。

---

## 8.4 第四阶段：治理决策

### 目标

将溢出机制转换成唯一治理方向。

### 映射关系

| 溢出机制                       | 决策模式                  | 允许生成的方案     |
| -------------------------- | --------------------- | ----------- |
| downstream_blocked         | downstream_protection | 下游保护、上游控流   |
| local_release_insufficient | incremental_release   | 目标方向小步增绿    |
| discharge_anomaly          | verify_then_adjust    | 核验方案、条件性增绿  |
| upstream_arrival_shock     | upstream_coordination | 上游削峰与目标小步释放 |
| evidence_insufficient      | verification_required | 补证任务        |

### 规则

* 策略包由确定性决策矩阵选择；
* 大模型不负责自由选择策略包；
* 每个 Case 只选择一个主决策模式；
* 只允许生成与该模式匹配的方案；
* 不再无条件生成三套候选。

当前系统会固定遍历“下游保护、小步释放、干线联控”三个方案。

这会导致无论当前事实是什么，都出现三套互相矛盾的场景。整改后应改为：

```python
for plan_type in decision.allowed_plan_types:
    build_plan(plan_type)
```

## 8.5 第五阶段：方案生成

### 目标

将治理决策编译为可以计算、校验和监测的方案。

### 方案类型

#### 核验方案

适用于：

```text
discharge_anomaly
evidence_insufficient
```

内容包括：

* 视频巡检对象；
* 逐周期观测对象；
* 检测器核验；
* 出口阻塞核验；
* 绿灯末端队列核验；
* 进入配时调整的前置条件。

#### 小步释放方案

适用于：

```text
local_release_insufficient
```

要求：

* 明确目标有效绿变化；
* 明确供时阶段；
* 周期原则上不变；
* 单阶段调整不超过阈值；
* 只运行有限观察周期；
* 配置回滚条件。

#### 下游保护方案

适用于：

```text
downstream_blocked
```

要求：

* 不得增加目标方向送车强度；
* 必要时减少目标有效绿；
* 可设置上游控制点；
* 监测直接下游恢复状态；
* 下游恢复后才允许转入释放策略。

#### 上游协调方案

适用于：

```text
upstream_arrival_shock
```

要求：

* 必须存在真实上游控制点；
* 必须明确控流对象；
* 必须计算上游新增排队风险；
* 不允许只有方案名称，没有上游控制参数。

# 九、策略到方案的语义编译要求

## 9.1 目标有效绿定义

目标转向可能存在于多个搭接阶段。

因此不能只检查某一个阶段是否增绿，而应计算：

```text
目标转向在完整周期内获得的有效绿总量
```

例如北向南直行同时存在于阶段 3 和阶段 8，则：

```text
目标有效绿变化
=
优化后北直总有效绿
-
现状北直总有效绿
```

不能出现：

> 策略写“北直增加 5 秒”，但某一个北直阶段增加 6 秒、另一个减少 13 秒，最终北直净减少。

## 9.2 方案契约必须进入求解器

以下字段必须成为硬约束或校验条件：

* `target_effective_green_delta_s`
* `cycle_delta_s`
* `max_stage_change_ratio`
* `target_movement_key`
* `immutable_stage_ids`
* `allowed_donor_stage_ids`
* `direct_downstream_inter_id`
* `upstream_control_required`
* `preconditions_satisfied`

当前优化器请求包含策略说明和目标饱和度，但尚不能证明最终结果严格满足目标绿灯变化和周期变化。

## 9.3 优化器不得覆盖治理意图

当前方案流程先生成轻量调整方案，再由单点优化器整体替换配时结果。

整改后可采用两种方式。

第一种是约束求解：

> 将策略契约转换成优化器硬约束。

第二种是后置语义校验：

> 优化器可以自由求解，但只要不符合策略契约，方案立即拒绝。

对于当前阶段，建议优先采用第二种，改动较小且更可靠。

# 十、方案护栏要求

方案必须同时通过三类护栏。

## 10.1 参数护栏

沿用现有能力：

* 周期上限；
* 最小绿；
* 最大绿；
* 黄灯；
* 全红；
* 行人清空；
* 回滚条件。

现有护栏主要校验这些基础参数。

## 10.2 溢出策略护栏

新增：

* 下游 blocked 时不得增加向下游送车；
* 下游 slack 时不得使用“下游接不住”作为方案依据；
* `verify_then_adjust` 未完成核验时不得输出 executable；
* 小步释放不得变成全局大幅重构；
* 上游协调必须有真实控制点；
* 下游保护必须包含下游恢复判据。

## 10.3 方案语义护栏

新增：

* 目标有效绿实际变化符合契约；
* 周期实际变化符合契约；
* 单阶段变化比例未超限；
* 供时阶段合法；
* 目标转向映射正确；
* 下游监测对象正确；
* 方案实际动作与名称一致；
* 不同候选不得使用完全相同的动作参数。

输出结构：

```json
{
  "parameter_validation": {
    "passed": true,
    "errors": []
  },
  "overflow_strategy_validation": {
    "passed": true,
    "errors": []
  },
  "semantic_validation": {
    "passed": true,
    "errors": []
  },
  "guardrail_pass": true
}
```

任一校验失败：

```text
guardrail_pass = false
```

不得成为推荐方案。

# 十一、试运行和反馈闭环

## 11.1 方案状态

系统应支持：

```text
verification_only
conditional
trial_ready
executing
validated
rolled_back
rejected
```

## 11.2 小步试运行

以 Case A 为例，核验通过后建议：

```json
{
  "target_effective_green_delta_s": 5,
  "cycle_delta_s": 0,
  "observation_cycles": 5,
  "max_stage_change_ratio": 0.15
}
```

## 11.3 监测指标

至少监测：

* 目标进口最大排队长度；
* 目标进口排队比；
* 目标方向每周期消散车辆数；
* 绿灯结束时剩余队列；
* 目标方向绿灯利用率；
* 直接下游排队长度；
* 直接下游排队比；
* 其他进口最大排队；
* 上游控制点排队；
* 行人清空是否正常。

## 11.4 成功条件

例如：

```text
目标进口排队比明显下降；
目标队列每周期可正常消散；
直接下游排队未明显上升；
其他进口未形成新的高风险排队；
连续多个周期表现稳定。
```

## 11.5 回滚条件

例如：

```text
直接下游排队持续增长；
目标方向有效绿增加后排队未改善；
其他进口排队逼近空间边界；
上游出现新溢出；
检测数据异常；
行人或安全约束异常。
```

## 11.6 反馈沉淀

每次试验应记录：

```json
{
  "case_fingerprint": {},
  "mechanism": "local_release_insufficient",
  "decision": "incremental_release",
  "actual_adjustment": {},
  "before_metrics": {},
  "after_metrics": {},
  "result": "accepted | rejected | rolled_back",
  "expert_comment": ""
}
```

经验只允许影响：

* 假设置信度；
* 调整步长；
* 观测周期；
* 监测指标；
* 回滚条件；
* 某类方案是否需要谨慎。

经验不得覆盖当前实时事实。

# 十五、验收标准

## 15.1 逻辑一致性

1. 同一 Case 全链路只存在一个目标路口、目标转向和直接下游。
2. 下游承接状态只存在一个结构化真源。
3. 诊断阶段只确认现象，不提前生成治理动作。
4. 成因阶段允许无法唯一归因。
5. 策略必须由机制确定性映射。
6. 方案只针对当前适用策略生成。
7. 最终配时必须证明自己符合策略。

## 15.2 Case A 验收

1. 结论为“溢出预警”，而不是无条件表述为实际外溢已完全确认。
2. 直接下游固定为永绥路与齐音路路口。
3. 不得引用奥体西路与解放东路路口作为北向南直行的直接下游。
4. 不得输出“下游接不住”作为当前确定结论。
5. 不得直接将“信号控制不当”标记为已确认主因。
6. 当前机制应为“放行效率异常待核验”或相同含义。
7. 当前策略应为“先验后调”。
8. 无核验结果时，不得输出可直接执行配时。
9. fixture 显式核验通过后，才允许进入小步增绿。
10. 小步增绿必须计算目标有效绿净变化。
11. 策略要求 +5 秒时，实际目标有效绿应接近 +5 秒，而不是净减少。
12. 策略要求周期不变时，最终周期变化必须为 0。
13. 任一阶段变化超过允许比例，方案不得通过。
14. 下游排队增长触发回滚。
15. 方案必须展示预期和实际调整差异。

## 15.3 可信性验收

每个关键结论必须附带：

* 事实依据；
* 数据来源；
* 数据质量；
* 置信度；
* 缺失证据；
* 是否可直接参与决策。

## 15.4 可执行性验收

任何标记为 `trial_ready` 或 `executable` 的方案都必须包括：

* 目标动作；
* 目标相位或目标转向；
* 调整量；
* 供时来源；
* 周期变化；
* 安全护栏；
* 监测指标；
* 观察周期；
* 成功条件；
* 回滚条件。

> 直接下游永绥路与齐音路路口当前排队较短、剩余蓄车空间较大，暂不支持下游整体承接不足。
> 目标进口高排队与低绿灯利用率并存，当前无法确认是单纯有效绿不足，重点核验出口通行、渠化与车道利用、检测有效性及上游到达时序。
> 当前采取“先验后调”，暂不直接生成可执行配时。
> 在确认下游畅通、检测正常且绿灯末端仍有未消散队列后，实施北向南直行有效绿增加约 5 秒、周期不变的小步试验。
> 连续观察 5 个周期；目标排队下降且直接下游无明显增长则保留，否则立即回滚。

最终系统的可信目标不是“每次都能生成方案”，而是：

> **有充分证据时生成可验证方案；证据不足时明确停止；方案生成后能够证明其与诊断、机制和策略完全一致。**
